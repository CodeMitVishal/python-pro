### 1. What is an ORM? Pros and cons?

**Say:** An Object-Relational Mapper maps tables to classes and rows to objects.
- **Pros**: less boilerplate, safe parameterised SQL, portability, relationships, migrations.
- **Cons**: it hides the SQL it runs (N+1), complex queries can be awkward, and there's some overhead.

Know the SQL it generates (`echo=True`).

---

### 2. What is the N+1 problem?

**Say:** You load N rows in 1 query, then a lazy-loaded relationship accessed in a loop runs N more queries. Fix it with eager loading: SQLAlchemy `selectinload` (a second query with IN) or `joinedload` (a JOIN), Django `select_related` / `prefetch_related`. Catch it with query-count tests.

---

### 3. What is a database index? When not to add one?

**Say:** A data structure (usually a **B-tree**) that finds rows in O(log n) instead of scanning the table. Add indexes on foreign keys and on columns used in WHERE, JOIN and ORDER BY. Skip them on tiny tables and low-selectivity columns (like booleans), and be careful on write-heavy tables: every index slows INSERT and UPDATE. Check with `EXPLAIN`.

**Follow-up:** *"Composite index column order?"* An index on `(user_id, created_at)` helps queries that filter by `user_id` (and sort by `created_at`). It doesn't help queries that filter only by `created_at` (the leftmost-prefix rule).

### 4. What are transaction isolation levels?

**Say:**
- **READ UNCOMMITTED** allows dirty reads.
- **READ COMMITTED** (the Postgres default) prevents dirty reads.
- **REPEATABLE READ** also prevents non-repeatable reads.
- **SERIALIZABLE** behaves as if transactions ran one after another; some transactions may fail and must be retried.

Higher isolation means fewer anomalies and less concurrency.

### 5. How do you prevent two users buying the last item (lost update)?

**Say:** Use an atomic conditional update, `UPDATE stock SET qty = qty - 1 WHERE id = :id AND qty > 0`, and check the affected rowcount. Alternatives are a row lock (`SELECT ... FOR UPDATE`, `.with_for_update()`) inside a transaction, or optimistic locking with a version column.

---

### 6. What is a Session in SQLAlchemy?

**Say:** A **unit of work** and identity map. It tracks the objects you add or change and flushes them in one transaction on `commit()`. Use one session per request (a FastAPI `yield` dependency) and never share one across threads.

---

### 7. What are migrations? How do you deploy schema changes safely?

**Say:** Versioned scripts (Alembic, Django migrations) that change the schema step by step, kept in git and applied in CI/CD. Keep changes **backwards compatible** so old and new code can run together during a deploy (expand → migrate data → contract). Review autogenerated scripts, test downgrade, and watch for long locks on big tables.

---

### 8. `joinedload` vs `selectinload`?

**Say:** `joinedload` adds a JOIN to the main query. It's good for many-to-one, but with one-to-many it duplicates parent rows. `selectinload` runs a second query `WHERE id IN (...)`, which is usually best for collections.

---

### 9. What is connection pooling?

**Say:** Keeping a set of open DB connections and reusing them, because opening a connection is slow. Configure `pool_size`, `max_overflow` and `pool_pre_ping` in `create_engine`. Make sure workers × pool size stays within the database's connection limit, or use PgBouncer.

### 10. Write SQL: the top 3 customers by revenue last month.

```sql
SELECT u.id, u.name, SUM(o.total) AS revenue
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at >= date_trunc('month', now()) - interval '1 month'
  AND o.created_at <  date_trunc('month', now())
GROUP BY u.id, u.name
ORDER BY revenue DESC
LIMIT 3;
```
